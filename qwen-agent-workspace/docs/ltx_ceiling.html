What the ceiling table would gate, by safety margin

The gate refuses a request whose frame count exceeds the measured ceiling for its resolution. The margin sets how much headroom under the 30.70 GiB cap a run must keep to qualify. A tighter margin is safer but omits more — and at 0.95 it omits the current default, 704×480, even though that resolution completes.

Three knobs: fps, frame rate, and the wide budget

Beyond frame count, three settings get conflated. Measured on identical seed and prompt, they turn out to do very different things — only one of them touches memory, and it is not the one people reach for first.

C is the decisive one: 704×480×57 aborts at the 0.82 budget (swap pressure) but completes at 0.87. Wide doesn't just raise a number — it gives near-cap runs enough Metal headroom to stop thrashing.
fps

Export frame rate is free — and memory-neutral

A vs A′ are the same frames (identical 409 KB file), re-exported at a different playback rate: 0 extra compute, 0 memory, just 4.04 s → 5.39 s. Dropping to 18 fps stretches a memory-bounded clip 33% longer; it does not raise the frame ceiling. Motion looks slightly less fluid, fine for short clips.

fr

Frame rate (conditioning) changes motion, not cost

A (fr 24) and B (fr 18) have identical peak (28.98 GiB) and wall time, but different motion: Δ 2.515 vs 2.219 (−12%). The model spaces movement to the declared rate. Keep frame rate = fps or the motion won't match the playback.

wide

The wide budget buys headroom, not speed

Raising the cap 30.7 → 32.6 GiB let 704×480×57 complete (29.85 GiB) where 0.82 aborted. The 92.5 s wall is the cost of more pixels, not of wide itself. This is the escape hatch for the resolutions the 0.98 table omits.

Resolution is the quality axis — same prompt, same seed, mid-clip frame. 384² is softer and square; 704×480 (wide) resolves finer detail and a wider frame.

Multi-image conditioning: what more keyframes cost

A run can be pinned to more than one image — a first-and-last frame, or arbitrary keyframes. Measured at 512×512×49, seed 0: adding conditions barely moves memory and doesn't move speed, but it is the main lever on motion. Conditioning is a motion-control tool, not a memory concern.

pin

Same-image keyframes stabilize; more pins = less motion

Pinning both ends to the same robot cut motion 1.93 → 1.05; three identical keyframes froze it to 0.20. Use repeated keyframes to hold a subject steady.

morph

Distinct endpoints drive interpolation

Robot @0 + a painting @48 pushed motion to 6.53 — a real morph. And it is asymmetric (C2): frame 0 is hard-pinned, the last frame is soft-guided, so the change is back-loaded — the painting only emerges toward the end.

New flags

--width --height --num-frames --fps --frame-rate --wide --last-frame --keyframe P:IDX[:STR] --allow-override. The override skips the ceiling table only — the watermark cap and sentinel still guard the host, so it is safe to force on a higher-capacity machine.

Robot → painting, the 2-distinct-condition run: frame 0 (hard), mid, frame 48 (soft-guided target). The morph is back-loaded, as the asymmetry predicts.

Chaining segments into a longer clip (W1)

A 6.12 s routine grown from a single still: each 2 s segment is seeded by the previous segment's last frame, three segments concatenated. Position is continuous across the seams; motion is not — the model re-infers movement from a still at each boundary, so the dance "resets" every 2 s. This is the cheap, no-new-code path; smooth motion continuity needs video-tail conditioning (not yet built).

Painting → seg 1 end → seg 2 end → seg 3 end. The static figure works into a crouched dance stance across the chain, drifting more abstract as autoregressive error accumulates. Every segment was content-screened and passed.

seam

Position continuous, motion reset

Seam deltas are low (seg1→2 1.45, seg2→3 1.16) because each segment starts exactly where the last ended. But intra-segment motion is ~3.6–4.2 and re-launches from a still at each boundary — a visible hitch every 2 s.

drift

Autoregressive drift compounds

Each segment conditions on the previous already-imperfect output, so detail softens and the figure grows more abstract by seg 3. W1 is good for a handful of segments, not indefinite length.

safe

Every segment screened

Each 2 s segment passed stage-3 content screening independently (nsfw 0.0007 / 0.0604 / 0.0025, zero frames flagged). A blocked segment would delete its frames and stop the chain — the gate is per-segment, not just per-final-clip.

Creation modes — CLI reference

All modes run through bin/ltx-generate, which does prep → generate → restore (servers down for the run, back up after — guaranteed even on failure). Positional form is <image> "<prompt>" [out.mp4]; flags go before it. Chaining is the one exception — still a script, noted last.

Single image → clip

Defaults: 704×480, 49 frames, 24 fps (~2 s).

bin/ltx-generate robot.png "the robot waves" out.mp4

Resolution & length

Smaller resolution buys more frames; width/height multiples of 32, (frames−1)%8==0. See the ceiling table above for the max frames per resolution.

bin/ltx-generate --width 384 --height 384 --num-frames 97 robot.png "dancing" out.mp4

Slower playback (longer, same memory)

Lower fps stretches a fixed frame budget; keep frame-rate == fps so motion matches. Zero memory effect.

bin/ltx-generate --fps 18 --frame-rate 18 robot.png "dancing" out.mp4

First + last frame (guided morph)

Frame 0 is hard-pinned; the last frame is soft-guided toward PATH — the change is back-loaded.

bin/ltx-generate --last-frame end.png start.png "morph" out.mp4

Keyframes (motion control)

Repeatable, PATH:INDEX[:STRENGTH]. Same-image keyframes pin/stabilize; distinct images interpolate. Each adds ~0.25 GiB peak.

bin/ltx-generate --keyframe mid.png:24 --keyframe end.png:48 start.png "routine" out.mp4

Wide budget (0.87)

Higher memory cap for resolutions the 0.82 ceiling omits (e.g. 704×704); skips the 0.82 table. The watermark cap + sentinel still guard the host.

bin/ltx-generate --wide --width 704 --height 704 img.png "scene" out.mp4

Override the ceiling table

Skip the measured pre-check only — for a higher-capacity machine where this host's table doesn't apply. Cap + sentinel remain; an over-budget run fails cleanly, never freezes.

bin/ltx-generate --allow-override --width 704 --height 480 img.png "scene" out.mp4

Resume (skip re-encoding)

Reuse a run whose stage-1 encode already succeeded; skips the T5 encode and any completed stages.

bin/ltx-generate --resume generated/ltx_runs/<ID> img.png "same prompt" out.mp4

Chaining into a longer clip (W1)

First-class tool. Seeds each segment from the previous last frame, concatenates, and does its own prep→restore (guaranteed). Each segment is content-screened; a blocked segment stops the chain. Position-continuous, motion resets per seam.

bin/ltx-chain start.png "a dance routine" out.mp4 --segments 4 --width 512 --height 512

Findings

01

The weight floor sets the whole band

The transformer alone is 24.29 GiB resident. Every completed run landed between 28.35 and 30.09 GiB — activations add only 4–6 GiB on top, so the entire ceiling question is about that thin margin under the cap.

02

Smaller resolution buys frames, fast

384×384 reaches 97 frames (~4.0 s at 24 fps) at just 28.98 GiB, while 704×480 tops out at 49 frames (~2.0 s). Halving the pixel area roughly doubles the clip length the budget allows.

03

The default resolution runs at the edge

704×480×49 peaks at 30.09 GiB — 98% of the cap, and the exact run that thrashed once on a cold host. It works, but with almost no headroom, which is why the 0.95 margin flags it.

04

704×704 is out of reach non-wide

Even 49 frames at 704×704 (3,388 tokens) tripped the sentinel before completing. This resolution needs the wider 0.87 budget — a separate table, not yet measured.

05

Failures were caught, never catastrophic

Over-budget cells failed as clean OOM at the hard cap or a sentinel abort on swap pressure — recorded as data. The host never froze; the watermark cap and the 2-second sentinel held on every cell.

Recommendation

Ship the gate at the 0.98 margin. It keeps every resolution that actually completes except 704×480 and 704×704, giving honest headroom without refusing the common mid-range sizes.

Keep 704×480 on the wide (0.87) budget rather than loosening the whole table to 1.00 for one edge case — that resolution is the one with a thrash on record, so a hard-cap run without margin is exactly where risk concentrates. The mps_guard sentinel remains the runtime backstop under any margin.
