## 1. Purpose and success criteria

### 1.1 Part 1 — multi-frame conditioning

`ltx_video_skill.py` line 310 hardcodes exactly one condition
(`conditions=[LTXVideoCondition(image=load_image(request["image_path"]), frame_index=0)]`), so
first-and-last-frame and keyframe conditioning are unreachable. Part 1 exposes them.

**Scope:** image conditions only. Video-clip conditioning (`LTXVideoCondition(video=...)`) is **out of
scope** and is a future follow-up (Section 12, F1). Everything specced here uses `image=`.

**Success criteria (Part 1).** The change is correct and complete when:

1. **Byte-for-byte back-compat.** An invocation with only a positional image (and optional prompt/output)
   produces a run whose `request.json`, `embeds.pt`, `frames/`, and mp4 are behaviorally identical to
   today's, and the stage-2 `conditions=[...]` list contains exactly one `LTXVideoCondition(image=...,
   frame_index=0, strength=1.0)`. No new keys are *required* in `request.json` to reproduce old behavior.
2. **Old `request.json` files still run.** A `request.json` written before this change (has `image_path`,
   has no `conditions` key) is accepted by stage 2 and resume without modification, normalizing to a single
   frame-0 condition.
3. **First+last frame.** `ltx-generate --last-frame B.png A.png "prompt" out.mp4` conditions frame 0 on `A.png`
   (hard) and frame `num_frames-1` on `B.png` (soft extra token — see C2), and produces a `num_frames`-frame mp4.
4. **Keyframes.** `ltx-generate --keyframe C.png:16 --keyframe D.png:32:0.7 A.png "prompt" out.mp4` conditions
   frame 0 on `A.png`, frame 16 on `C.png` (strength 1.0), frame 32 on `D.png` (strength 0.7).
5. **Validation refuses bad input** with the exact messages in Section 3.3 / 4.3 for: malformed `--keyframe`,
   out-of-range `frame_index`, out-of-range `strength`, a missing local file, and a duplicate `frame_index`.
6. **Stage 1 unaffected.** `embeds.pt` and its `meta` are unchanged; stage 1 never sees a conditioning image.
7. `tests/check_ltx_no_forbidden_calls.py` still passes against the edited `ltx_video_skill.py`.

### 1.2 Part 2 — resolution/frame ceiling sweep and gate

Today an over-ceiling `(width, height, num_frames)` is discovered only *mid-run*, by the stage-2 watermark
cap or the sentinel, after the operator has already prepped the host and paid for stage 1. Part 2 measures
the true host ceiling at fraction 0.82 and adds a cheap, earlier refusal.

**Success criteria (Part 2).** Correct and complete when:

1. `tests/measure_ltx_ceiling.py` runs a grid of cells, each a **real** stage-2 in its own subprocess,
   reusing one precomputed `embeds.pt`, and appends one JSONL result per cell to
   `generated/ltx_ceiling/results.jsonl` with outcome + measured peaks + wall time.
2. The sweep is **freeze-proof by construction** (Section 7.4): each cell inherits the stage-2 watermark cap
   and sentinel unchanged, so an over-ceiling cell fails as a clean OOM or a sentinel abort (exit 75), never
   a freeze; and each cell is isolated in its own subprocess.
3. The sweep **refuses to run if the vLLM servers are up** (reuses `mps_guard` gates via the real stage-2

4. A documented **reduction** step turns `results.jsonl` into `ltx_ceiling.json` — no hand-editing.
5. `generate_video` consults `ltx_ceiling.json` **before spawning any stage** and refuses a request that
   exceeds the measured ceiling, naming the max supported frames for that resolution and suggesting a lower

6. The reproduced anchor cell **704×480×49 completes** with peak `mps_driver_gib ≈ 30.09` (± 0.5),
   `max_compressor_gib ≈ 23.5` (± 2), matching the session's ground truth.

## 3. Part 1 — data model and validation

### 3.1 `request.json` schema (new canonical shape)

A run's `request.json` gains one new key, `conditions`, a non-empty JSON array of condition objects.
Every other key is unchanged. The legacy top-level `image_path` key is **retained** (it is still the
frame-0 / primary image, and is still consulted by resume and by `_release_page_cache`).

Condition object shape (all three keys always present in a freshly written `request.json`):

```json
{ "image_path": "<absolute path or URL>", "frame_index": 0, "strength": 1.0 }
```

Example freshly written `request.json` for a first+last-frame run:

```json
{
  "image_path": "/abs/A.png",
  "prompt": "the robot waves",
  "negative_prompt": "worst quality, inconsistent motion, blurry, jittery, distorted",
  "output_path": "/abs/out.mp4",
  "width": 704, "height": 480, "num_frames": 49,
  "num_inference_steps": 8, "guidance_scale": 1.0,
  "fps": 24, "frame_rate": 24, "seed": 0, "wide": false,
  "conditions": [
    { "image_path": "/abs/A.png", "frame_index": 0,  "strength": 1.0 },
    { "image_path": "/abs/B.png", "frame_index": 48, "strength": 1.0 }
  ]
}
```

**Invariant:** `conditions[0]` is always the primary image at `frame_index 0, strength 1.0`, and its
`image_path` always equals the top-level `image_path`. This keeps resume's `image_path` check meaningful.

### 3.2 Normalization (back-compat read path)

Add a module-level helper to `ltx_video_skill.py`:

```
def _normalized_conditions(request):
    """Return the list of condition dicts for a request, tolerating the
    legacy single-image shape. Never mutates `request`."""
    conditions = request.get("conditions")
    if conditions:
        return conditions
    return [{"image_path": request["image_path"], "frame_index": 0, "strength": 1.0}]
```

Rules:
- If `conditions` is present and non-empty → return it verbatim.
- Else (old-style request, or absent/empty) → synthesize the single frame-0 condition from `image_path`.
- Called by `_stage2_denoise` (Section 5) and by the sweep tool. Guarantees old `request.json` files run.

### 3.3 Validation (`_validate_conditions`)

Add a module-level helper, called from `generate_video` immediately after `_validate_geometry`
(Section 5). Signature and rules:

```
def _validate_conditions(conditions, num_frames):
    """Raise ValueError naming the offending value and the rule it broke."""
```

Checks, in this order, over the assembled list of condition dicts:

1. **Non-empty.** `len(conditions) >= 1` (always true by construction; defensive).
2. **frame_index type + range.** For each condition, `frame_index` must be an `int` with
   `0 <= frame_index <= num_frames - 1`. On failure:
   `"frame_index=%r is out of range: must satisfy 0 <= frame_index <= num_frames-1 = %d" % (frame_index, num_frames-1)`
   **No 8-alignment is required** (see C1): image conditions are placed at raw pixel coordinates.
3. **strength type + range.** `strength` must be a real number with `0.0 <= strength <= 1.0`. On failure:
   `"strength=%r is out of range for %s: must satisfy 0.0 <= strength <= 1.0" % (strength, image_path)`
4. **Local file existence.** If `image_path` contains no URL scheme (`"://" not in image_path`), require
   `os.path.isfile(image_path)`. On failure:
   `"conditioning image not found: %s" % image_path`. URLs (`"://" in image_path`) are not existence-checked
   here (they are resolved by `diffusers.utils.load_image` in stage 2, matching current behavior).
5. **No duplicate frame_index.** The set of `frame_index` values must have no repeats. On failure:
   `"duplicate frame_index=%d: each condition must target a distinct output frame" % frame_index`
   (Rationale: two conditions at the same index would either overwrite the same hard latent slot or stack
   ambiguous soft tokens; refusing is deterministic and safe.)

### 3.4 Semantics note the executor must preserve (do not "fix")

Per C2 (Section 11): frame 0 is **hard** conditioning (written into the latent grid); any non-zero
`frame_index` is **soft** conditioning (an extra attention token at that coordinate). "First+last frame"
is therefore asymmetric: the first frame is pinned, the last frame is guided. This is the diffusers 0.40.0
behavior; the spec conditions to it and does not attempt to make the endpoints symmetric.

### 4.4 `--keyframe` SPEC parsing (`_parse_keyframe_spec`)

Add a module-level helper. Grammar: `PATH:INDEX[:STRENGTH]`, where PATH may itself contain `:` (macOS paths
rarely do, but robustness is required). Parse from the **right**:

```
def _parse_keyframe_spec(spec):
    """Parse 'PATH:INDEX[:STRENGTH]' -> dict. Raise ValueError on malformed input."""
    parts = spec.split(":")
    if len(parts) < 2:
        raise ValueError(_KEYFRAME_ERR % spec)
    # Try PATH:INDEX:STRENGTH (last two numeric), else PATH:INDEX (last numeric).
    def _is_int(s):  ...   # int(s) succeeds
    def _is_float(s): ...  # float(s) succeeds
    if len(parts) >= 3 and _is_int(parts[-2]) and _is_float(parts[-1]):
        return {"image_path": ":".join(parts[:-2]),
                "frame_index": int(parts[-2]),
                "strength": float(parts[-1])}
    if _is_int(parts[-1]):
        return {"image_path": ":".join(parts[:-1]),
                "frame_index": int(parts[-1]),
                "strength": 1.0}
    raise ValueError(_KEYFRAME_ERR % spec)
```

with the module constant:

```
_KEYFRAME_ERR = ("malformed --keyframe %r: expected PATH:INDEX[:STRENGTH] "
                 "where INDEX is an integer and STRENGTH is a float in [0.0,1.0]")
```

Range/existence checks for the parsed values are **not** done here; they are done centrally by
`_validate_conditions` (3.3) once the full list is assembled, so all error phrasing lives in one place.
A malformed-grammar failure (`ValueError` from `_parse_keyframe_spec`) in the `__main__` path must be caught,
its message printed to stderr, and `sys.exit(2)`.

### 4.5 Flag interaction rules

- `--last-frame` and `--keyframe` may be combined; the resulting conditions are: primary (frame 0), then
  the last-frame condition (if any), then keyframes in the order given. `_validate_conditions` will reject a
  keyframe whose `frame_index == num_frames-1` when `--last-frame` is also set (duplicate index rule 3.3.5)
  — this is the desired, deterministic failure.
- The positional `<image_path>` is always the frame-0 primary and is mandatory; `--last-frame`/`--keyframe`
  never replace it.

## 7. Part 1 — memory analysis, and its coupling to Part 2

### 7.1 Resident-weight impact: none

Conditioning images are VAE-encoded to latents in stage 2 only. A single 704×480 image encodes to a latent
of shape `[1, 128, 1, 15, 22]` = 42 240 elements × 2 bytes (bf16) ≈ **0.08 MiB**. Even a dozen conditions is
< 1 MiB of latent storage against 26.61 GiB of resident weights. The VAE **encoder activations** for one
704×480×1 frame are transient and small relative to the decoder pass (which framewise-decodes the full
output). **So the user's claim "N conditioning images add negligible resident memory" is correct for the
latent storage.**

### 7.2 CORRECTION — non-zero-index conditions DO move the stage-2 peak (C3)

Every condition with `frame_index != 0` appends **one latent frame's worth of tokens** to the transformer
sequence: `tokens_extra = (H/32) × (W/32)`. At 704×480 that is 15 × 22 = **330 tokens**. The base sequence
for 49 frames is `latent_frames × 330 = 7 × 330 = 2310` tokens. A single last-frame condition raises it to
**2640 tokens (+14.3%)**. Transformer self-attention memory/compute scales ≈ **O(tokens²)**, so the attention
activation for that step grows ≈ **+30%**.

The anchor 704×480×49 already peaks at **30.09 / 30.70 GiB (98% of cap)** with frame-0-only conditioning.
Therefore a last-frame or keyframe condition at that resolution **can push stage-2 peak over the cap** and
trip the watermark/sentinel. Consequences the executor and operator must understand:
- **Case (a), frame-0-only:** zero token delta, zero measurable peak change — byte-for-byte safe.
- **Cases (b)/(c):** measurable peak increase; near the ceiling they can exceed it.

### 7.3 `mps_guard` G1 gate: unchanged (confirmed)

The G1/G1a/G1b preflight requirement is `cap_gib + PREFLIGHT_OVERHEAD_GIB`, where `cap_gib = fraction ×
recommended_max`. Conditioning does **not** change the cap, the overhead constant, or the fraction — so
**G1 needs no change** (the user's belief is confirmed). What conditioning changes is whether *activations*
fit **under** the fixed cap; that is bounded by the watermark cap (hard) and backstopped by the sentinel, not
by G1. This is exactly why Part 2 exists: to refuse over-ceiling `(w,h,frames)` before spawning, rather than
discovering it at the cap mid-run.

### 7.4 Coupling to the ceiling table

Because of C3, the ceiling table (Part 2) is measured **frame-0-only** and is annotated
`"conditioning": "frame0-only"` in its meta. A run that adds non-zero-index conditions has *less* headroom
than the table implies. The gate (Section 8) therefore applies a **conditioning derate**: for each condition
with `frame_index != 0`, subtract its token contribution when comparing against the measured ceiling. See
Section 8.4 for the exact, conservative rule. (This keeps the table small and honest instead of trying to
measure the full conditioning cross-product.)

```json
    "conditioning": "frame0-only",
    "cap_gib": 30.70,
    "safety_margin_frac": 0.95,
    "host_total_gib": 48.0,
    "diffusers_version": "0.40.0"
  },
  "ceiling": {
    "384x384": 121,
    "512x512": 97,
    "704x480": 49
  }
}
```

- `ceiling` keys are `"<width>x<height>"`; values are the max `num_frames` that COMPLETED with
  `peak_mps_driver_gib <= safety_margin_frac × cap_gib` **and** no sentinel abort (Section 9.5).
- A `(w,h)` for which even the smallest tested frame count fails the criterion is **omitted** from `ceiling`
  (not written as 0), so absence is unambiguous.

### 8.2 Gate function `_check_ceiling`

Add to `ltx_video_skill.py`:

```
def _check_ceiling(width, height, num_frames, conditions, wide):
    """Refuse (raise mps_guard.HostSafetyError) a request that exceeds the
    measured non-wide ceiling. No-op when wide=True or the table is absent."""
```

Called in `generate_video` after `_validate_conditions`, before building/writing the request. Behavior:

1. **`wide is True` → return immediately.** The 0.82 table does not apply to a 0.87 run (Section 8.5).
2. **Load the table.** If `CEILING_TABLE_PATH` is missing or unparseable → print a one-line warning to
   stderr (`"[ltx_video_skill] note: %s absent/unreadable; skipping ceiling pre-check (mps_guard remains
   the backstop)"`) and **return** (do not refuse — I6 back-compat; mps_guard is the runtime backstop).
3. **Resolve the effective max frames for `(width, height)`** using the deterministic rule in 8.3.
   If the rule yields "unmeasured/unbounded" → refuse (message R1).
4. **Apply the conditioning derate** (8.4) to `num_frames` → `effective_frames`.
5. If `effective_frames > max_frames_for_res` → refuse (message R2).
6. Else return (pass).

### 8.3 Resolution lookup rule (deterministic)

Let `key = "%dx%d" % (width, height)` and `C = table["ceiling"]`.

1. If `key in C` → `max_frames = C[key]`.
2. Elif there exists at least one measured `(w,h)` in `C` with `w <= width and h <= height` →
   `max_frames = min(C[wh] for those)`. (A larger canvas is strictly more expensive, so its ceiling is
   ≤ that of any smaller-or-equal measured canvas; the min is the tightest safe bound.)
3. Else → **unmeasured/unbounded** → refuse with R1.

### 8.4 Conditioning derate (conservative)

Non-zero-index conditions add tokens (C3). Convert the added tokens back into an equivalent number of output
frames and add them to the request's frame count for the comparison:

```
extra_conditions = number of conditions with frame_index != 0
# Each adds one latent frame of tokens; one latent frame == vae_temporal_compression_ratio (8) output
# frames of transformer sequence cost, to first order.
effective_frames = num_frames + extra_conditions * 8
```

Compare `effective_frames` against `max_frames_for_res`. This over-counts slightly (safe direction) and needs
no second table. Document the derate constant (8) as `_CEILING_FRAMES_PER_CONDITION = 8` with a comment
citing C3.

### 8.5 Refusal messages

R1 (unmeasured resolution):
```
HOST SAFETY REFUSAL: resolution %dx%d has no measured ceiling entry and no smaller measured
resolution to bound it. Measured resolutions: %s. Run the sweep
(tests/measure_ltx_ceiling.py) for this resolution, choose a measured resolution, or pass --wide.
```
R2 (frames exceed ceiling):
```
HOST SAFETY REFUSAL: %dx%d supports at most %d frames at the non-wide (0.82) budget, but this
request asks for %d frames (effective %d after conditioning derate). Reduce num_frames to <= %d,
choose a lower resolution, or pass --wide for the higher (0.87) budget.
```
Both raise `mps_guard.HostSafetyError` so they surface through the existing parent-side
`"HOST SAFETY REFUSAL:"` marker handling (ltx_video_skill.py lines 611–623) — but note `_check_ceiling`
runs in the **parent** process (`generate_video`), so the `HostSafetyError` propagates directly as an
exception from `generate_video`; the marker-scanning code only applies to subprocess logs. The message text
still begins with `HOST SAFETY REFUSAL:` for consistency.

### 8.6 Precedence vs `mps_guard`

The ceiling gate is **first, cheapest, and advisory-to-safety**: it runs in the parent before any prep cost
is spent and before any subprocess spawns. It **never** replaces the stage-2 preflight (G0/G1/G2) or the
watermark cap or the sentinel — those still run in the stage-2 subprocess exactly as today and remain the
authoritative runtime backstop. If the table is stale/absent the gate defers entirely to mps_guard (8.2 step
2). A request may pass the ceiling gate and still be refused by a stage-2 preflight gate (e.g. because Chrome
is holding memory) — that is correct and unchanged.

### 8.7 `--wide` interaction

`ltx_ceiling.json.meta.wide = false`. `_check_ceiling` is a no-op when `wide is True`. A future
`ltx_ceiling_wide.json` at fraction 0.87 is **out of scope** (Section 12, F2). Until it exists, `--wide`
runs are gated only by mps_guard. Document this in the `_check_ceiling` docstring.

**Pre-existing limitation to note, not fix:** `wide` is currently reachable only via the `generate_video`
Python API (`kwargs["wide"]`); neither `ltx_video_skill.py __main__` nor `bin/ltx-generate` expose a
`--wide` flag today. `_check_ceiling` keys off `request`'s `wide` value (the source of truth), so it is
correct regardless. Wiring `--wide` through the CLI is out of scope (Section 12, F3).

### 9.4 Sweep algorithm

1. **Encode once.** Create a base run dir
   `generated/ltx_ceiling/_base-<UTC timestamp>-<uuid8>/`, write a `request.json` for the **first geometry
   in the grid** (geometry is irrelevant to embeds — I2 — but a valid request is required), with the fixed
   prompt, `DEFAULT_NEGATIVE_PROMPT`, the `--image` as the single frame-0 condition, `seed=0`, `wide=false`.
   Run stage 1 by spawning the real skill: `subprocess.run([sys.executable,
   ltx_video_skill.__file__, "--stage", "1", "--run-dir", base_dir])`. On nonzero rc, abort the sweep with
   the child log. If `--skip-stage1-if-present` and `base_dir/embeds.pt` exists (from a prior base dir passed
   explicitly — see note), reuse it. (The tool discovers the most recent `_base-*` dir when
   `--skip-stage1-if-present` is set and no fresh encode is requested.)
2. **Per cell** `(w, h, n)`, ascending `n` within each resolution:
   a. Create cell dir `generated/ltx_ceiling/<w>x<h>x<n>-<uuid8>/`.
   b. Copy `base_dir/embeds.pt` into the cell dir (a real copy, not a symlink, so a cell's cleanup can
      never touch the shared file). `shutil.copyfile`.
   c. Write the cell's `request.json`: same prompt/negative_prompt/image/conditions/seed as base, but with
      this cell's `width/height/num_frames`, `wide=false`, `output_path=None` (no mp4 needed; we only need
      frames written + peaks). `num_inference_steps=ltx_video_skill.DEFAULT_STEPS`,
      `guidance_scale=DEFAULT_GUIDANCE`, `fps/frame_rate=24`.
   d. Spawn the **real stage 2**: `subprocess.run([sys.executable, ltx_video_skill.__file__, "--stage", "2",
      "--run-dir", cell_dir], stdout=PIPE, stderr=STDOUT, text=True)`, wall-timed with `time.monotonic()`.
   e. **Classify** by return code + artifacts:
      - `rc == 0` → `"completed"`. Read `peaks_stage2.json` for peak metrics.
      - `rc == mps_guard.SENTINEL_EXIT_CODE` (75) → `"sentinel_abort"`; peaks still present; also capture the
        `sentinel_abort` reason from `mem_stage2.jsonl`.
      - `rc != 0` and child log contains `"HOST SAFETY REFUSAL:"` → `"host_not_ready"`: **abort the whole
        sweep** (the host is not correctly prepped; continuing would mislabel every subsequent cell). Print
        the refusal block and `sys.exit(3)`.
      - other `rc != 0` → `"oom_or_error"`. This is the expected outcome for an over-ceiling cell that hits
        the hard MPS watermark cap (a caught `RuntimeError` from Metal). Record peaks if `peaks_stage2.json`
        exists, else nulls.
   f. Compute `swap_growth_gib` from `mem_stage2.jsonl` (last `swap_used_gib` − first `swap_used_gib`; 0.0 if
      unavailable).
   g. Append one JSONL line (9.6) to the results file, flushed immediately (`f.write(...); f.flush()`).
   h. **Early-exit per resolution:** if outcome is not `"completed"`, or peak
      `mps_driver_gib > cap_gib` (i.e. it only survived by luck), **stop escalating `n`** for this resolution
      and move to the next resolution. Cost is monotone increasing in `n`, so a larger `n` at the same
      resolution cannot succeed if this one did not. Record the skipped larger `n` cells as `"skipped"`
      (outcome `"skipped"`, no peaks) so the JSONL is complete, or omit them — **decision: omit them** to keep
      the file to actually-run cells; the reducer treats absence as "not supported".
   i. Optionally delete the cell's `frames/` after recording (they are large) but keep
      `request.json`, `mem_stage2.jsonl`, `peaks_stage2.json`, `stage2.log` for forensics. **Decision:**
      delete `frames/` (`shutil.rmtree`, best-effort) to bound disk; keep the small forensic files.
3. After all cells, print the summary table (9.7).

`cap_gib` used in 2.h and the derate is computed as `mps_guard.FRACTION_STAGE2 *
mps_guard._recommended_max_gib()` sampled once at startup (requires torch/MPS; if MPS unavailable the tool
prints `"REFUSING: MPS not available; the sweep measures MPS behavior."` and `sys.exit(2)`).

### 9.5 (reserved — reduction is 9.5 below the algorithm) 

### 9.6 `results.jsonl` line schema

One JSON object per run cell:

```json
{
  "width": 512, "height": 512, "num_frames": 97,
  "latent_frames": 13, "tokens": 3120,
  "outcome": "completed",
  "peak_mps_driver_gib": 29.8, "min_supply_gib": 6.1,
  "max_compressor_gib": 21.4, "swap_growth_gib": 0.6,
  "cap_gib": 30.70, "wall_s": 412.3, "rc": 0,
  "sentinel_reason": null,
  "ts": "2026-08-25T00:00:00Z"
}
```

- `latent_frames = (num_frames - 1)//8 + 1`; `tokens = latent_frames * (width//32) * (height//32)`.
- `outcome ∈ {"completed","sentinel_abort","oom_or_error"}`.
- peak fields come from `peaks_stage2.json` keys `mps_driver_gib` / `min_supply_gib` / `max_compressor_gib`;
  null if the file is absent.

### 9.5 Reduction (`--reduce`)

Reads `results.jsonl`; groups by `(width,height)`; for each group selects the **largest** `num_frames` whose
row satisfies **all** of: `outcome == "completed"` **and** `peak_mps_driver_gib <= margin * cap_gib`
(margin default 0.95, cap from the row's `cap_gib`). Emits `ltx_ceiling.json` (8.1 schema). Groups with no
qualifying row are omitted from `ceiling`. `meta.generated_at` is now; `meta.cap_gib` is the modal `cap_gib`
across rows; `meta.safety_margin_frac` is the `--margin`. Prints, per resolution, the chosen max frames and
the peak at that frame count, plus any omitted resolutions.

### 9.7 Summary table (printed at end of sweep)

Sorted by `(width, height, num_frames)`. Columns: `WxH | frames | outcome | peak_drv | comp | supply |
swap_grow | wall_s`. After the table, a per-resolution line: `MAX COMPLETING <= 0.95*cap: WxH -> N frames`
(or `WxH -> none`).

### 9.8 Freeze-proofness (state explicitly in the module docstring)

The sweep cannot freeze the host because:
1. **Each cell is the real stage 2**, which calls `mps_guard.set_watermark(0.82)` as its first act, setting
   `torch.mps.set_per_process_memory_fraction(0.82)` — a **hard** cap. An over-ceiling allocation fails as a
   caught Metal `RuntimeError` (clean nonzero exit), it cannot grow past the cap into a freeze. The
   2026-08-25 freeze happened at the 1.7 default, i.e. with **no** cap; here every cell has the cap.
2. **The stage-2 `Sentinel` runs in every cell**, backstopping CPU-side growth the watermark does not bound
   (`os._exit(75)`).
3. **Each cell is its own subprocess**; a cell that `os._exit`s or segfaults cannot corrupt the sweep loop
   or the next cell. The parent only reads the child's rc + on-disk artifacts.
4. **The tool never raises or lowers a `mps_guard` threshold** and never bypasses preflight.

## 11. Corrections to the requester's framing

- **C1 — image frame indices are NOT floored to the 8-frame grid, and need no alignment.** The user asked to
  check whether a non-aligned `frame_index` is "silently rounded or rejected" and to validate to match. The
  installed source shows the `// 8` floor (line 739) is inside the `num_data_frames > 1` (video) branch only.
  For a single image, `frame_index == 0` hard-writes latent frame 0, and `frame_index != 0` places an extra
  token at the **raw** pixel coordinate `frame_index` (line 566) — no floor, no rounding, no rejection. So
  our validation requires only `0 <= frame_index <= num_frames-1` (Section 3.3 rule 2); **do not** add an
  8-alignment requirement for image conditions. (The user's "map to latent frame `frame_index // 8`"
  statement is true only for the out-of-scope video path.)
- **C2 — "first+last frame" is asymmetric.** Frame 0 is hard conditioning; the last frame (any non-zero
  index) is soft (an extra attention token). "First+last frame" pins the first and *guides* the last. This is
  diffusers 0.40.0 behavior; the spec conditions to it (Section 3.4) rather than forcing symmetry.
- **C3 — the Part-1 memory claim is only half right.** Latent *storage* for N conditioning images is
  negligible (< 1 MiB), as claimed. But each non-zero-index condition adds `(H/32)×(W/32)` tokens to the
  transformer sequence, and attention scales ≈ O(tokens²). At the 704×480×49 anchor (already 98% of cap), a
  last-frame/keyframe condition can push stage-2 peak over the cap. So stage-2 peak **does** move measurably
  for cases (b)/(c) — just not for case (a). G1 still needs no change (7.3), but the effective headroom under
  the cap shrinks, which is precisely why the ceiling table carries a `frame0-only` annotation and the gate
  applies a conditioning derate (8.4). **Scrutinize this if measured behavior disagrees.**
- **C4 — the anchor line references are accurate but line 310 is the only functional edit.** Confirmed:
  changing `conditions=[...]` at line 310 (Section 5) is the entire pipeline-call change; the memory model and
  three-process split are untouched, matching the user's Part-1 point 4.
- **C5 — output content-safety screening is currently DISABLED.** Lines 368–375 of `ltx_video_skill.py` have
  the `assert_frames_safe` call **commented out**, so the module docstring's claim that output is screened is
  presently inaccurate. This affects Part-1 point 7 (see Section 13).
- **C6 — `--wide` is not reachable from any CLI today.** Neither `__main__` nor `bin/ltx-generate` sets
  `wide`; it is Python-API-only. The ceiling gate keys off the request's `wide` value so it is correct
  regardless, but wiring `--wide` to the CLI is a separate change (out of scope, F3).
