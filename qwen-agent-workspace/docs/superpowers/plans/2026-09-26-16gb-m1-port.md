# 16GB M1 MacBook Pro Port Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Get the existing story→image→video pipeline running on a 16GB M1 Pro/Max MacBook Pro, in seed-image mode, with the smallest model variants that plausibly fit — validated for real on the target hardware, not just predicted.

**Architecture:** No pipeline code changes. Three real-hardware validation tasks (in strict order, each gating the next) confirm the leanest model set actually works, then a final task writes a setup script and a docs file using the real numbers those validations produced.

**Tech Stack:** `ltx-2-mlx` CLI (already installed via `uv sync --all-extras` per its own README), `hf` CLI (huggingface_hub) for model downloads, this repo's existing `bin/ltx-movie` / `bin/story-server` / `bin/ltx-mlx-render`.

**Spec:** `docs/superpowers/specs/2026-09-26-16gb-m1-port-design.md` (committed `c0f1977`, corrected in `351111c`)

## Global Constraints

- Target machine: a 16GB M1 Pro/Max MacBook Pro, **not** the 48GB M5 Pro development machine this plan was written on. Tasks 1-3 can only be executed once that machine is available and accessible — they are not runnable in the authoring session.
- No changes to `bin/ltx-movie`, `ltx2_mlx_video_skill.py`, `bin/story-server`, or any other pipeline code (spec §5). Every task uses existing flags/env vars only.
- No reuse of `scripts/deploy/build_pkg.py` / `install_pkg.py` (spec §5) — this is a single hand-set-up machine.
- Video DiT: `dgrauet/ltx-2.3-mlx-q4`, distilled transformer only (`transformer-distilled.safetensors`, 11,322,002,285 bytes) — never `transformer-dev.safetensors` or either LoRA file (unused under `--distilled`, per this project's own established convention).
- Text encoder: `mlx-community/gemma-3-12b-it-qat-abliterated-lm-4bit` (~6.85GB). **Updated 2026-09-26 (real hardware):** the originally-planned `mlx-community/gemma-3-12b-it-4bit` OOM'd on the real target machine; this QAT variant is confirmed stable there, paired with the unchanged video DiT (`dgrauet/ltx-2.3-mlx-q4`), at `-W 640 -H 384 --frames 169 --frame-rate 24`.
- Vision LLM: `alexgusevski/Huihui-Qwen3-VL-4B-Instruct-abliterated-q4-mlx` (~3.1GB).
- Downloads use plain `hf download <repo>` (never `--local-dir`) so `huggingface_hub` manages its own `blobs/`+`snapshots/` cache layout — a real corruption incident this same session (a flat, non-standard directory from `--local-dir`, which broke model resolution and required manual repair) must not be repeated on the target machine.
- Never invent a final `--min-avail-gib`, geometry, or `iogpu.wired_limit_mb` value — every number that ships in Task 4's deliverables must trace back to a real measurement from Tasks 1-3.
- If any task's real-hardware step fails its stated pass criterion, STOP that task and do not proceed to the next — report the failure and reconsider, per spec §6. Do not silently substitute a workaround.

## Review Focus

- **A stalled/hung download being mistaken for progress.** This exact class of bug (a progress bar showing a misleadingly low file-count percentage while gigabytes are actively transferring) was hit for real this session — Task 1's download step calls this out explicitly so whoever runs it doesn't kill a healthy transfer.
- **OOM killing the process outright vs. heavy swapping that merely slows it down.** Task 1's pass/fail criteria distinguish these — a swap episode that resolves is not the same failure as a hard kill, and conflating them would either abandon a viable port or accept a genuinely broken one.
- **The `--min-avail-gib` default (25.0) silently refusing to even start** on a 16GB machine — every real invocation in Tasks 1-3 must pass an explicit low override or it never gets past the precondition check at all.
- **Reusing the dev machine's hardcoded absolute paths.** Every path in this plan for the target machine is relative to that machine's own `$HOME`, not `/Users/reubenpatterson/...` — the setup script (Task 4) must derive paths, never hardcode this session's dev-machine username.
- **A frame count that isn't on the LTX distilled pack's valid lattice.** This project's own prior notes record that frame counts must satisfy an `8k+1` pattern for the 2.3 distilled pipeline; Task 2's chosen frame count is checked against this explicitly rather than picked arbitrarily.

### Task 1: Download the core video models and run the text-encoding-stage smoke test

**Files:** none created or modified — this is a real-hardware validation task. Runs on the target 16GB M1 Pro/Max machine only.

**Interfaces:**
- Consumes: nothing from an earlier task (this is the first task).
- Produces: a recorded peak-memory/swap measurement for the Gemma+connector text-encoding stage, which Task 2 needs to pick its own `--min-avail-gib` probe value, and which Task 4 needs for the real (non-probe) value shipped in the setup script and docs.

- [ ] **Step 1: Confirm `ltx-2-mlx` is installed on the target machine.**

```bash
which ltx-2-mlx || { git clone https://github.com/dgrauet/ltx-2-mlx.git ~/ltx-2-mlx-tool && cd ~/ltx-2-mlx-tool && uv sync --all-extras; }
ltx-2-mlx --help | head -5
```
Expected: a usage banner for `ltx-2-mlx`, no error. If `uv` itself isn't installed, install it first per `https://docs.astral.sh/uv/getting-started/installation/` — this is a one-time host prerequisite, not part of this plan's own deliverables.

- [ ] **Step 2: Download the video DiT pack's needed files only (skip `transformer-dev`, both LoRAs, and the upscalers).**

```bash
mkdir -p ~/hf_cache
export HF_HOME=~/hf_cache
hf download dgrauet/ltx-2.3-mlx-q4 \
  --include "connector.safetensors" \
  --include "transformer-distilled.safetensors" \
  --include "audio_vae.safetensors" \
  --include "vae_decoder.safetensors" \
  --include "vae_encoder.safetensors" \
  --include "vocoder.safetensors" \
  --include "config.json" \
  --include "embedded_config.json" \
  --include "quantize_config.json" \
  --include "split_model.json"
```
Expected: `hf download` completes with no error, prints a final local snapshot path. This downloads roughly 19.6GB (10.54GB transformer + 6.34GB connector + ~1.7GB of VAE/audio/vocoder/config files) — confirm with:
```bash
du -sh "$(hf download dgrauet/ltx-2.3-mlx-q4 --include "connector.safetensors")"
```
(the second call is a cache-hit no-op that just prints the same resolved directory; `du -sh` on it should read approximately 19-20G, not 50-60G — if it's close to 50-60G, the `--include` filters didn't take effect and `transformer-dev`/the LoRAs downloaded too; stop and fix the include list before proceeding, don't just let the extra ~35GB sit there unused.)

**Do not use `--local-dir` on this or any download in this plan.** Let `hf download` manage its own cache under `$HF_HOME` normally.

- [ ] **Step 3: Download the Gemma-3 text encoder.**

```bash
hf download mlx-community/gemma-3-12b-it-qat-abliterated-lm-4bit
```
Expected: completes with no error, roughly 6.85GB downloaded. (Updated 2026-09-26: the original `mlx-community/gemma-3-12b-it-4bit` OOM'd on real hardware; this QAT variant is the confirmed-working replacement.)

- [ ] **Step 4: Attempt the smoke test first WITHOUT raising the GPU wired-memory cap, to find out whether the raise is even necessary.**

Check the current cap:
```bash
sysctl iogpu.wired_limit_mb
```
Record this value. Do not change it yet.

Start a background memory sampler first:
```bash
( while true; do date +%s; sysctl vm.swapusage; sysctl kern.memorystatus_vm_pressure_level 2>/dev/null; sleep 1; done > ~/16gb-port-task1-memlog.txt 2>&1 & echo $! > ~/16gb-port-task1-memlog.pid )
```

Then run the smallest practical real generation (9 frames — the smallest value on the `8k+1` lattice this pack's frame-count convention requires per this project's own prior notes; `--low-ram` on; a `--min-avail-gib` probe value near zero, since this step's only job is to observe whether the process itself survives, not to validate the real safe threshold yet):
```bash
ltx-2-mlx generate -p "A single red apple sitting on a wooden table" \
  --distilled --model dgrauet/ltx-2.3-mlx-q4 \
  --height 320 --width 192 --num-frames 9 \
  --low-ram \
  -o ~/16gb-port-task1-test.mp4
```

Stop the sampler once the command above exits (success or failure):
```bash
kill "$(cat ~/16gb-port-task1-memlog.pid)"
```

**Pass criterion:** the command exits 0 and `~/16gb-port-task1-test.mp4` exists and is a non-empty, playable file. Read `~/16gb-port-task1-memlog.txt` and identify the peak `used` value in the `vm.swapusage` lines that occurred *before* the console output shows the transformer/DiT starting to load (the exact log line that marks this transition isn't known in advance from the dev machine — watch the live console output and note the wall-clock second where DiT-loading activity visibly starts, e.g. a "Loading transformer" or similar line, then cross-reference against the memlog's timestamps to isolate the pre-DiT window). Record this peak swap-`used` value and note whether `kern.memorystatus_vm_pressure_level` ever left its normal/green state during that window.

**If the process is OOM-killed** (check `dmesg`/Console.app for a jetsam kill, or the shell reports a bare "Killed" with no other output) during the text-encoding stage specifically (before any DiT-loading activity is visible in the console) — do not give up yet. Proceed to Step 5 (raise the wired-memory cap and retry once) before treating this as a final fail.

If the process completes successfully without raising the cap: record that the raise was **not necessary** at the default cap, note the peak swap-`used` value, and skip Step 5 entirely (go straight to Step 6).

If the process completes successfully but `kern.memorystatus_vm_pressure_level` showed sustained pressure (not just a brief transient blip) during the text-encoding window, treat this as a soft warning, not a hard fail — record it, and factor it into Task 2's `--min-avail-gib` choice (pick a more conservative, higher probe value in Task 2 than you otherwise would have).

- [ ] **Step 5: If Step 4 OOM-killed, raise the wired-memory cap once and retry.**

```bash
sudo sysctl iogpu.wired_limit_mb=14336
```
(14336 MB = 14GB, leaving roughly 2GB for macOS itself on a 16GB machine — this is a starting value to test with, not a value with prior validation; adjust upward only if this specific value still fails, and downward if the machine becomes unresponsive at this setting.) Requires a real terminal session with sudo access on the target machine (not this session, which has no TTY for sudo).

Rerun the exact Step 4 generate command and memory sampler. If it now completes successfully, record that the raise **was necessary**, note the peak swap-`used` value from this run, and note the exact `iogpu.wired_limit_mb` value used. If it OOMs again even with the cap raised, **STOP** — this is the single highest-risk unknown the whole spec calls out (spec §6, step 1), and the LTX-2 model family may not be viable on this 16GB machine at all. Do not try a smaller Gemma variant or any other workaround without first reporting this back and getting a fresh decision, per the spec's own explicit instruction not to silently substitute a fix here.

- [ ] **Step 6: Check whether the wired-memory cap raise (if it was needed) persists across a reboot.**

Only do this if Step 5 was needed and succeeded. Reboot the target machine, then check:
```bash
sysctl iogpu.wired_limit_mb
```
If it reverted to the pre-raise value, the setup script (Task 4) needs a persistence mechanism (a LaunchDaemon or a `/etc/sysctl.conf` entry — pick based on what's actually needed, don't guess this now) rather than a one-shot command. Record which is true.

- [ ] **Step 7: Record the result.**

Write the peak swap-`used` figure, the pass/fail verdict, whether the wired-memory cap raise was necessary and if so its exact value and whether it persists across reboot, and whether memory pressure was observed, into a plain-text note at `~/16gb-port-task1-result.txt` on the target machine (this file is scratch for this plan's own later tasks to read; it is never committed to the repo). This is the number Task 2 and Task 4 both need.
